# DVS 作者使用手册

先运行[青禾书店最小角色卡](../assets/dvs-minimal-card/README.md)，再沿本手册把它改成自己的卡。示例只有成年店员林溪的基本设定、开场白、世界书和 DVS 脚本，记录好感度、时间地点和随身物品，不需要状态栏或 EJS 插件。

SQLite Helper 负责数据库读写和文件保存；DVS 为每条 AI 回复管理一份状态，把起点交给正文模型，并在正文完成后请求变量模型更新。作者决定表结构、初值、字段含义和变化规则。安装、存储模式与更新先按[使用与维护指南](helper-usage.md)完成；接口细节在[DVS 接口与进阶用法](dvs-api.md)中按需查阅。

## 从完整示例开始

需要随卡提供插件安装提示时，可另行附带[安装引导脚本](installer-guide.md)，与 DVS 注册脚本分开保留；这项内容可选。

按示例的[README](../assets/dvs-minimal-card/README.md)导入 [card.json](../assets/dvs-minimal-card/card.json)。它的可编辑来源是 [index.yaml](../assets/dvs-minimal-card/index.yaml)、[开场白](../assets/dvs-minimal-card/welcome.txt)、[DVS 脚本](../assets/dvs-minimal-card/dvs.js)及世界书文件；导入包由这些来源生成。修改源文件后重新生成，避免同时手改来源和导入包。

先打开示例的专用新聊天，确认脚本启用、初始化查询和一次变量更新都能完成，再修改内容。已有聊天不会因改了 INIT 就重新初始化。

| 作者操作 | 应得到的结果 |
| --- | --- |
| 确定设定及需要变化的内容 | 静态人物设定与动态字段各有用途 |
| 写 DDL 和 INIT | 表结构、初值和开场白一致 |
| 组织世界书 | 正文看到当前状态，变量模型看到规则和起点 |
| 注册业务键与两个准备回调 | DVS 能定位每行，并准备两次请求的数据 |
| 生成正文、查询结果 | 表名、键、字段及实际变化可核对 |
| 修改字段并升级 | 新聊天和已有聊天都按明确版本取得新结构 |

## 从设定确定表和业务键

林溪是青禾书店的 24 岁店员，用户是来访者。人物身份放在[人物设定](../assets/dvs-minimal-card/worldbook/person.txt)；会随剧情变化的值才进入数据库。

| 表 | 业务字段 | 在一份状态中怎样定位一行 | 初值 |
| --- | --- | --- | --- |
| 人物 | 姓名、好感度 | 姓名 | 林溪，好感度 10 |
| 场景 | 编号、时间、地点 | 编号，固定为“当前” | 2026-10-19 15:00，青禾书店 |
| 物品 | 名称、数量 | 名称 | 林溪随身的帆布包 1、书签 2 |

这里的定位字段叫业务键，注册时写入 `uniqueKeys`。姓名定位“林溪”，不是它的数据库行编号。物品表统一表示林溪随身的物品；同名物品合并数量，不能在同一份状态中有两个同名行。需要区分不同持有人或不同实例时，应先决定自己的业务含义，再相应修改表和业务键。

每张真实表另有 `rid`：它是 16 字节 BLOB 主键，区分同一对象不同时间的记录。DVS 正常写入时生成 `rid`，模型不用提供它。业务表保留历史行，因此不要给姓名、物品名称等业务键加全表 SQL `UNIQUE`；它们只要求在目标 AI 回复的有效集合中唯一。

## 为角色卡准备 SQL

打开示例的 [ddl.sql](../assets/dvs-minimal-card/worldbook/ddl.sql) 和 [init.sql](../assets/dvs-minimal-card/worldbook/init.sql)：

1. DDL 创建业务表及字段约束。示例好感度为 0–100，物品数量是大于 0 的整数；这些是该卡的规则，由 SQLite 约束实际写入。
2. INIT 插入开场白起点，使用 `randomblob(16)` 产生初始 `rid`。初始化数据必须与[开场白](../assets/dvs-minimal-card/welcome.txt)相符。
3. 在角色卡绑定的主世界书或附加世界书中，将它们分别登记为精确名称 `[DVS_DDL]v1.0.0` 和 `[DVS_INIT]welcome_0`。SQL 条目保持禁用，DVS 仍会读取；内容可有多条 SQL，不自行写 `BEGIN`、`COMMIT` 或 `ROLLBACK`。

条目名中的 `1.0.0` 只是示例，作者也可以从 `[DVS_DDL]v0.1.0` 开始。已有聊天不会自动降级；修改起始版本不代表会重新执行其初值。

第一次打开新聊天，DVS 先执行 DDL，再执行对应开场白的 INIT，并为它建立数据关联。重新打开不会重复插入；切回已有初始化状态的开场白会读取原值。`welcome_0` 对应默认开场白，额外开场白依次用 `welcome_1`、`welcome_2`。多个开场白、INIT 省略和用户名字占位符 `{{user}}` 的完整规则见[初始化参考](dvs-api.md#为角色卡准备-sql)。

## 选择世界书条目的用途

示例在 [index.yaml](../assets/dvs-minimal-card/index.yaml) 中登记以下条目，正文来源仍在各自文件中维护：

| 条目 | 内容来源 | 开关与用途 |
| --- | --- | --- |
| `[DVS_DDL]v1.0.0` | [ddl.sql](../assets/dvs-minimal-card/worldbook/ddl.sql) | 禁用；创建或迁移表结构 |
| `[DVS_INIT]welcome_0` | [init.sql](../assets/dvs-minimal-card/worldbook/init.sql) | 禁用；插入开场白初值 |
| 人物设定 | [person.txt](../assets/dvs-minimal-card/worldbook/person.txt) | 启用常驻；正文和变量请求共用静态背景 |
| `[DVS_NAR]当前状态` | [narrative.txt](../assets/dvs-minimal-card/worldbook/narrative.txt) | 启用常驻；给正文提供当前状态 |
| `[DVS_RULES]更新规则` | [rules.txt](../assets/dvs-minimal-card/worldbook/rules.txt) | 启用；说明字段含义和变化条件 |
| `[DVS_DATA]变量数据` | [data.txt](../assets/dvs-minimal-card/worldbook/data.txt) | 启用；给变量模型提供本轮起点 |

正文条目用 `[[DVS_DATA]]` 或分表宏取得本次准备好的数据。规则写“发生什么，改哪张表、哪个字段，怎样改变”，并交代数值边界、时间格式、物品耗尽时移除等业务含义；数据条目用宏提供实际起点，不手写一份会过时的当前值。DVS 自动提供表名、业务键、字段名和补丁协议，不必再复制一套输出格式。

`[DVS_NAR]` 只参加正文；`[DVS_VAR]` 可用于只参加变量请求的普通设定。无这两个标签或同时有两个的普通设定可供两边使用，仍遵守酒馆的激活规则。`[DVS_RULES]`、`[DVS_DATA]` 则直接读取已启用条目，不靠关键词激活；SQL 不进入两次提示词。进阶的标签组合、检查项和扫描规则见[世界书参考](dvs-api.md#选择世界书条目的用途)。

## 可选：检查主世界书版本

玩家更新角色卡后，当前关联的主世界书可能仍是旧版。作者可在卡片元信息中填写版本，并在主世界书中放置唯一、名称精确为 `[DVS_VERSION]` 的条目，内容只写版本，例如 `0.2.0`；该条目可以禁用。这里的卡片／世界书内容版本与 DDL 迁移版本各自维护。

需要此功能时，在卡内另放一个独立酒馆助手脚本，启动时调用一次：

```js
await waitGlobalInitialized('DVS');
await DVS.lorebookVersionCheck({ onExpired: 'WARNING_MESSAGE' });
```

`WARNING_MESSAGE` 在主书版本落后时，提示玩家先保留修改，再从角色卡重新导入并关联。要自动更新，显式改成 `'AUTO_UPDATE'`：发现较旧主书后先显示原生确认框，列出书名和双方版本，说明将另名保留全部本地修改。取消则结束，不读取内嵌来源、不写入数据。点击“备份并更新”后，DVS 从卡片内嵌世界书导入新版并保留完整旧书；成功框会显示新书、版本及旧书名，玩家可自行取回修改。

该脚本不需要 `dvs_enable` 或业务注册，也不保证先于变量注册脚本运行；版本检查不会暂停注册。成功后点击“刷新页面”才会重新加载整个酒馆页面，让新版及卡片脚本重新生效；按 Esc 或关闭成功框不会刷新。失败时仍显示错误提示，不刷新；按提示核对已保存的旧书、新书与当前关联，再手工处理，不会自动重试。版本格式、读取范围、更新顺序和失败结果见[接口参考](dvs-api.md#主世界书版本检查)。

## 注册与查询

角色卡只绑定一个 DVS 注册脚本。查看示例 [dvs.js](../assets/dvs-minimal-card/dvs.js)，它依次等待 `waitGlobalInitialized('DVS')`、传入自身 `getScriptId()` 注册，并在页面卸载时调用返回的释放函数。

在这个脚本的酒馆助手预设定变量中设置 `{ "dvs_enable": true }`，并启用角色卡脚本及其文件夹。这里只接受布尔值 `true`，字符串 `"true"` 和数字无效；改动后按助手原生方式重载脚本。等待公共接口可用不等于已启用卡片功能，关闭时不会注册或初始化。

注册的 `uniqueKeys` 与上表逐项一致：`人物: ['姓名']`、`场景: ['编号']`、`物品: ['名称']`。两个准备回调都不能省略：

| 回调 | 用途 | 最小卡的处理 |
| --- | --- | --- |
| `narrativePrepare({ tables })` | 正文生成前准备宏数据 | 返回 `tables` |
| `beforeGen(_state, tables)` | 变量模型请求前准备宏数据 | 返回 `tables` |

这两个返回值只影响相应提示词，不会直接修改数据库。没有确定的业务计算时，无需增加其他回调或虚拟表。需要隐藏提示词字段或在写入前计算时，查[回调参考](dvs-api.md#数据准备和更新回调)。

注册完成后，可在当前角色的酒馆助手脚本中查询：

```js
const state = await DVS.getState();
const person = await state.table('人物').get('林溪');
const scene = await state.table('场景').get('当前');
const items = await state.table('物品').orderBy('名称', 'asc').rows();
console.log(JSON.stringify({ person, scene, items }));
```

`get()` 按注册业务键的完整顺序传值，没有匹配返回 `null`。无参 `getState()` 取最近 AI 回复当前 swipe 的状态；该回复尚无关联时会报错，不偷偷退回旧回复。历史查询和多字段业务键见[查询参考](dvs-api.md#注册与查询)。

## 正文数据注入

正文模型按照人物设定和当前状态续写；`narrativePrepare` 返回的数据通过正文世界书中的 DVS 宏送入提示词。最小示例不使用 EJS，只需酒馆助手及本插件。

| 操作 | 正文和随后变量更新使用的起点 |
| --- | --- |
| 发送下一句，正常追加回复 | 最近 AI 回复当前 swipe 的状态 |
| 重新生成末尾普通 AI 回复、生成它的新 swipe | 被替换回复之前的 AI 回复状态 |
| 末尾是用户消息时重新生成 | 仍按追加取值 |
| 只有已初始化的开场白时生成后续正文 | 当前开场白状态，不重跑 INIT |

例如林溪的好感度在 A 回复后是 10，B 回复后变为 12。正常接着 B 写从 12 出发；重新生成 B 从 A 的 10 出发。作者不需要自己计算上一层，也不要在准备回调中无条件再读一次 `DVS.getState()` 来替代收到的起点。

总表宏默认 Markdown；`[[DVS_DATA_人物:yaml]]` 可只输出人物表的 YAML。只修改返回的数据副本，就只影响本次提示词。宏格式、序列化错误和可选 EJS 查询的边界见[正文注入参考](dvs-api.md#正文数据注入)。

## 配置变量模型

从插件设置打开“DVS 变量模型设置”，填写 OpenAI 兼容服务的基础地址、模型名及按需填写的密钥；地址不包含末尾 `/chat/completions`。保存普通参数后按界面结果核对。可以测试连接与输出格式，测试最多三次请求，可能产生费用，但不会读取聊天或更新变量。

普通参数保存在酒馆账户设置中；密钥以明文保存在当前 SQLite 存储空间。密码框留空表示保持已有密钥；清除须使用清除选项。切换存储空间后重新核对密钥状态，读取失败不等于没有密钥。参数范围、输出格式、密钥保存结果及可选开场白配置表单见[配置参考](dvs-api.md#配置变量模型)。

## 检查一次完整更新

1. 在专用新聊天运行上面的查询。初值应与 INIT 一致：人物林溪／10，当前场景的时间地点，以及两行随身物品。
2. 发送一句会引起明确变化的行动，等待正文完整生成。通过酒馆的提示词查看入口核对正文收到实际起点；SQL、变量专用规则不应混入正文。
3. 等待变量处理结束。在回复尾部展开“查看变量更新”，检查 `Analysis`、`UpdateCommands` 的表名、完整业务键和字段。这里是模型原始建议，不是全部写入成功的证明。
4. 再查数据库实际值，核对命令是否正确执行、数量和好感度是否满足该卡约束。不把模型建议的某个具体好感度数值当成 DVS 功能是否正常的唯一标准。
5. 重新生成最新普通回复或生成新 swipe，核对起点来自前一个 AI 回复；切回原 swipe，仍应读到它自己保存的状态。
6. 单独核对保存：管理方法或查询成功只证明当前 Worker 内的数据，不证明 SQLite 文件已落盘。先处理插件报告的后台保存失败，再按[保存与检查说明](helper-author-guide.md)检查文件或关闭全部相关页面后重新打开读取；聊天关联与数据库文件也不是同一事务。

正文正常完成后自动请求变量模型，停止或生成失败不触发。只支持单人聊天的普通生成、重新生成最新回复和新 swipe；续写、冒充用户、群聊、工具递归和助手独立请求不在支持范围内。

### 主动更新最新回复的变量

在角色卡作者脚本中调用 `await DVS.regen()` 可重算最新 AI 回复当前 swipe 的变量，不重新生成正文。普通回复仍从前一 AI 回复开始；只有开场白时从全部注册表为空开始，忽略已有值且不重跑 INIT。因此它不能用来“恢复原 INIT”。

处理期间暂不能发送下一轮，可以点击酒馆停止按钮；取消不撤销已提交修改。自动重试、停止后的结果和进度接口见[变量更新参考](dvs-api.md#主动更新最新回复的变量)。

## 角色卡升级

如果给人物增加“备注”，新聊天和已有聊天都要取得这个字段。不要只编辑已执行过的 `v1.0.0` 或修改 INIT 来期待旧聊天重跑。

1. 保留旧 DDL，新增禁用的 `[DVS_DDL]v1.1.0`，内容例如 `ALTER TABLE "人物" ADD COLUMN "备注" TEXT NOT NULL DEFAULT '';`。新聊天依次执行两个版本，旧聊天只执行高于已成功版本的迁移。
2. 检查 INIT 是否需要显式设置备注；这里可以省略并使用默认空字符串。若改变初值，同步开场白；旧聊天已有业务值按迁移 SQL 处理。
3. 在世界书中说明备注含义和何时更新，检查正文数据是否需要包含它。表和业务键不变时无需改 `uniqueKeys`；改名、拆表或换键则同步修改 DDL、数据、索引和脚本声明。
4. 原生重载脚本后分别检查一个新聊天和一个已有聊天。普通连续查询最多可缓存 3 秒世界书，重新注册会重新读取。

迁移版本必须是完整三段 SemVer，按升序逐版本提交；当前版本失败会停止后续版本，保留先前成功版本，不自动降级。新增表及 `[[last_fid]]` 索引关联的完整写法见[迁移参考](dvs-api.md#角色卡升级)。

## 错误与保存

| 看到的情况 | 应怎样处理 |
| --- | --- |
| 未启用或未注册 | 检查布尔开关、脚本启用和当前角色绑定，再原生重载 |
| 表不存在、字段或业务键不符 | 对照 DDL、`uniqueKeys`、世界书字段和迁移版本 |
| 正文准备失败 | 修正回调或宏；请求会停止，原生已加入的用户消息不会自动撤回 |
| 变量模型失败，已沿用上一 AI 回复 | 本轮业务变化没有完成，先检查规则／请求错误，再决定是否 `regen()` |
| 结果无法确认、`unknown` | 不直接重发 SQL，按已知提交结果和实际读回核对 |
| 数据库已提交，对象刷新或后处理失败 | 已提交部分保留，重新 `getState()` 查询，不能当作全部回滚 |
| 初值已提交，聊天关联失败 | 不自动重跑 INIT，需要核对数据库与聊天关联 |

完整 DVS 结果边界见[错误与保存参考](dvs-api.md#错误与保存)，公共错误字段和后续处理见[错误说明](helper-errors.md)。聊天复制独立身份、导入编号处理和完整备份恢复尚未提供；不要把复制或导入的聊天自动当成独立数据库。其余限制见[支持范围](dvs-api.md#支持范围)。
