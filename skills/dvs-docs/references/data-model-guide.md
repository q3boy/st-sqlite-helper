# 数据结构

## 新增数据表

例如，给已有卡增加“任务”表，保存任务编号、标题和状态。先决定旧聊天如何开始使用它：从空任务列表开始，还是在当前楼层补入某条任务。新功能不一定需要给所有历史楼层补同样的数据。

### 修改来源文件

| 要改的内容 | 本例怎样修改 |
| --- | --- |
| DDL | 保留原版本，新增更高版本条目，例如 `[DVS:DDL]v1.1.0` |
| 注册脚本 | 在原 `uniqueKeys` 中增加 `任务: ['编号']`，其余表保留 |
| 各开场白 INIT | 按该开场白的设定加入任务初值，或者明确保持任务表为空 |
| 变量规则 | 写清何时建立任务、何时完成或取消，以及“计划做”是否算已经建立 |
| 变量数据 | 使用总表宏时会包含返回的任务表；使用分表宏时补上 `[[DVS_DATA_任务:yaml]]` |
| 正文与界面 | 需要展示任务时增加相应读取；准备回调若逐表构造返回值，也要检查是否包含任务 |

下面的迁移先建立任务表及其楼层索引。楼层索引记录“哪个回复状态使用哪些历史行”，只建业务表还不足以让已有状态读到新行。

```sql
CREATE TABLE "任务" (
  rid BLOB PRIMARY KEY CHECK(typeof(rid)='blob' AND length(rid)=16),
  编号 TEXT NOT NULL,
  标题 TEXT NOT NULL,
  状态 TEXT NOT NULL DEFAULT '进行中'
);
CREATE TABLE IF NOT EXISTS "_dvs_index_任务" (
  fid BLOB NOT NULL CHECK(typeof(fid)='blob' AND length(fid)=16),
  rid BLOB NOT NULL CHECK(typeof(rid)='blob' AND length(rid)=16),
  PRIMARY KEY(fid,rid)
) WITHOUT ROWID;
```

如果旧聊天从空任务列表开始，这段 SQL 已够用。如果作者决定给当前状态加入“整理书架”，在同一个迁移条目末尾加入：

```sql
INSERT INTO "任务"(rid,编号,标题,状态)
SELECT randomblob(16),'整理书架','整理书架','进行中'
WHERE [[last_fid]] IS NOT NULL;
INSERT INTO "_dvs_index_任务"(fid,rid)
SELECT [[last_fid]],rid FROM "任务"
WHERE [[last_fid]] IS NOT NULL;
```

这里的“任务”是本版本新建的空表，所以第二条语句关联本次新行。不要把这段写法直接套到已有且保存了多份历史记录的表上。

`[[last_fid]]` 是 DVS 提供的迁移标记：有当前状态时替换为该状态编号；全新聊天时替换为 `NULL`。它放在 SQL 值的位置，外面不加引号。因此全新聊天只建表，随后由该开场白的 INIT 插入初值；已有聊天执行更高版本迁移，不重跑 INIT。完整规则见[角色卡升级](dvs-api.md#角色卡升级)。

### 改完怎样检查

分别检查专用新聊天和已有聊天的副本。新聊天应得到该开场白的初值；已有聊天应保留原表数据，并按你选择的方案得到空任务表或当前楼层的新任务。查询新表时通过 `DVS.getState()`，不要用“数据库里有一行”代替“当前状态能读到这一行”。

如果选择只关联当前状态，更早的历史楼层没有这些任务是预期结果。确实需要补历史时，先定义每个历史状态应有什么，再编写对应迁移；不能用统一初值冒充当时发生过的事情。

## 修改字段或业务键

先分清是增加字段、改名，还是改变“一行代表什么”。这三种操作对旧数据的影响不同。

例如给物品增加备注，不改变物品的识别方式，可以新增一个 DDL 版本：

```sql
ALTER TABLE "物品" ADD COLUMN 备注 TEXT NOT NULL DEFAULT '';
```

旧历史行会获得空备注，原来的 `rid` 和楼层关联保留。同步修改各开场白 INIT、变量规则，以及实际需要显示备注的正文或界面。规则要说明“没有提到备注时保持原值”，不要让模型每轮重新编写。业务键没有变化，就无需重写 `uniqueKeys`。

| 改动 | 还要核对什么 |
| --- | --- |
| 新增字段 | 旧行默认值是否合适，新聊天初值是否一致，回调有没有固定列清单 |
| 字段改名 | SQL、`uniqueKeys`、规则、宏涉及的表、回调和界面查询中是否还有旧名 |
| 删除字段或改变类型 | 旧值怎样保留或转换；若重建表，保留每条历史记录原来的 `rid` 及其关联 |
| 业务键变化 | 每个有效状态中是否仍能唯一定位；筛选数据、查询与模型规则是否使用完整新键 |
| 表改名 | 注册表名、SQL、宏、回调、查询以及 `_dvs_index_<表名>` 是否同时对应 |

例如从物品“名称”改为“持有人＋名称”，要明确旧物品归谁，先迁移持有人值，再将注册改为 `物品: ['持有人', '名称']`。后续查询、筛选和补丁都要提供两个键，不能只在注册中多加一项。

保留已发布的旧 DDL，新增更高版本；新聊天会按版本依序建表和迁移，再执行 INIT。已有聊天只执行尚未成功的更高版本。检查时既看当前状态，也看保留的旧楼层，不能用删除数据库或重跑 INIT 验证升级。更复杂的表重建与关联要求见[角色卡升级](dvs-api.md#角色卡升级)。
